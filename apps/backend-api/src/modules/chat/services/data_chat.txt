TremBot — Canonical Behavior Specification
What Trem Means (Locked)

TREM = Tours + Reservations + Experience + Management

TremBot is not a generic chatbot.
It is a domain-specific assistant with role-aware behavior.

1️⃣ TremBot High-Level Behavior Model

TremBot always does three things in order:

Detect user category

Detect intent

Route to the correct domain engine

User Categories (Authoritative)
User Type	Access Level
Free User	Tours
Authenticated User	Tours + Reservations
Member (Employee / Agent)	Tours + Reservations + Management
Any User	Experience (Help / Feedback)

This is rule-based access control, not ML.

2️⃣ The 4 Core Domains (Authoritative)
🔹 A. TOURS (Free Users)

Who: Anyone 
Nature: Informational + Recommendation
Risk: Low
Hallucination tolerance: Zero (prices, days must be exact)

Supported Behaviors

Tour details

Price queries

Filters (city, budget, duration, people)

Featured / popular tours

Comparison

Rule-Based (Major)

✔ Intent detection
✔ Feature extraction
✔ Slot filling (ask missing inputs)
✔ Filtering logic
✔ City fallback
✔ Price bounds

ML-Based (Optional, Later)

◻ Ranking tours by relevance
◻ Understanding messy phrasing
◻ Paraphrasing responses

Decision:
👉 Tours = 90% rule-based, 10% ML

🔹 B. RESERVATIONS (Authenticated Users)

Who: Logged-in users
Nature: Transactional
Risk: High
Hallucination tolerance: ZERO

Supported Behaviors

Find my tour

Find booking by PNR / Tour ID

Hotel / flight lookup

Booking status

Cancellation policy

Rule-Based (ALL)

✔ Authentication check
✔ ID / PNR validation
✔ Database lookup
✔ Exact response formatting
✔ Error handling

ML-Based

❌ NONE

Why:
ML must never touch transactional correctness.

Decision:
👉 Reservations = 100% rule-based

🔹 C. MANAGEMENT (Members / Employees)

Who: Internal users
Nature: Operational
Risk: Very high
Hallucination tolerance: ZERO

Supported Behaviors (Future)

Employee details by ID

Assigned tours

Availability

Internal notes

Staff-related queries

Rule-Based (ALL)

✔ Role-based access
✔ Permission checks
✔ Deterministic queries

ML-Based

❌ NONE (except analytics later)

Decision:
👉 Management = 100% rule-based

You were absolutely right to defer this.

🔹 D. EXPERIENCE (Everyone)

Who: Customers, agents, employees
Nature: Conversational + Support
Risk: Low
Hallucination tolerance: Medium

Supported Behaviors

Feedback submission

Help center queries

FAQs

Escalation to human

Sentiment capture

Rule-Based (Major)

✔ Flow control
✔ Ticket creation
✔ FAQ routing
✔ Escalation rules

ML-Based (Useful)

✔ Sentiment analysis
✔ Feedback categorization
✔ Auto-tagging
✔ Smart FAQ matching

Decision:
👉 Experience = 70% rule-based, 30% ML

3️⃣ TremBot Decision Tree (Very Important)

Every request follows this logic:

Request
 └── Is user authenticated?
      ├── No → Tours / Experience only
      └── Yes
           ├── Is it reservation-related?
           │     └── Rule-based lookup
           ├── Is user a member?
           │     └── Management logic
           └── Otherwise → Tours / Experience


This is deterministic AI routing.

4️⃣ Slot Filling Is CORE Rule-Based AI

Your example:

“Give me top tours”

Correct TremBot behavior:

Detect intent → TOUR_RECOMMENDATION

Detect missing slots:

city

budget

duration

persons

Ask only what’s missing

Store answers in context

Execute query when complete

This is classical AI called:

Slot Filling / Dialogue State Management

No ML required.

5️⃣ What ML Is Allowed to Do in TremBot (Strict)

ML is never the decision-maker.

ML can only assist with:

Area	ML Role
Tours	Ranking, language flexibility
Experience	Sentiment, categorization
Feedback	Topic clustering
Search	Semantic matching

ML must never:

Fetch bookings

Decide prices

Confirm reservations

Access management data

Rules always have the final authority.

6️⃣ Final TremBot Philosophy (Memorize This)

“TremBot is a domain-aware, role-aware assistant. Core business logic is rule-based for correctness and explainability. Machine learning is used selectively to enhance
language understanding and user experience, never to control critical decisions.”

This is a very strong product + engineering statement.
